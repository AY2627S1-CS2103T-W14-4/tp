Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, ClientListPanel, GigListPanel, PaymentObligationListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts. Selecting a client in ClientListPanel passes that client to GigListPanel, which filters the observable gig list by the client's stable identifier and renders each gig's title, status, deadline, and fee. Selecting a gig then passes it to PaymentObligationListPanel, which shows that gig's due-date-ordered payments and their paid, outstanding, or overdue display states. MainWindow also switches these panels into the cross-client gigs, deadlines, and outstanding overview modes based on flags carried by CommandResult.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Client, Gig, and PaymentObligation objects from the model.
  • displays gigs and payments for the current selection without changing the client filter used by commands.

Logic component

API : Logic.java

Here's a (partial) class diagram of the Logic component:

The sequence diagram below illustrates the interactions within the Logic component, taking execute("delete 1") API call as an example. The command resolves the index against the currently displayed client list and passes the selected Client to the model. Invalid indexes and clients with associated gigs are rejected; only a successful deletion creates a CommandResult. Note: The lifeline for DeleteClientCommandParser should end at the destroy marker (X), but due to a limitation of PlantUML, the lifeline continues till the end of diagram.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to a GigabyteParser object, which in turn creates a parser that matches the command (e.g., DeleteClientCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteClientCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a client).
    The command may make several calls to the Model; interactions within the model are omitted from this diagram.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

How the parsing works:

  • When called upon to parse a user command, the GigabyteParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddClientCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddClientCommand). The GigabyteParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddClientCommandParser and DeleteClientCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.
  • AddGigCommandParser parses one displayed client index plus t/, s/, d/, and f/ fields. AddPaymentCommandParser parses displayed client and per-client gig indexes plus a/ and d/ fields. Both reject missing or repeated single-valued prefixes before their commands update the model.
  • EditGigCommandParser accepts a displayed client index, a per-client gig index, and at least one of t/, d/, or f/. DeleteGigCommandParser accepts the two indexes only. FindGigCommandParser accepts title keywords. SetGigStatusCommandParser parses two indexes and one s/ field. EditPaymentCommandParser parses three indexes and at least one of a/ or d/; DeletePaymentCommandParser, MarkPaymentPaidCommandParser, and MarkPaymentUnpaidCommandParser parse three indexes only. FilterGigsCommandParser parses one s/ field. deadlines needs no arguments, while outstanding explicitly rejects arguments. Overview commands return CommandResult view instructions that MainWindow applies without changing the current client filter.

Model component

API : Model.java

The Model component,

  • stores all Client, Gig, and PaymentObligation objects. Clients are contained in a UniqueClientList; gigs and payment obligations are exposed as unmodifiable observable lists.
  • stores the Client objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Client> that the UI can observe and bind to, so the UI updates when the list changes.
  • uses stable UUIDs to preserve links from each gig to its client and from each payment obligation to its gig. Client edits replace linked immutable objects while retaining those identifiers and links. Payment edits replace the selected immutable obligation while preserving its canonical gig and paid state. Payment-status changes replace the exact immutable obligation while retaining its gig, amount, and due date.
  • replaces gigs through Model#setGig when details or status change. GigabyteData#setGig relinks dependent payments to the replacement object. EditGigCommand preserves the gig UID, client, status, and payments; a deadline edit refreshes and can reorder the deadline overview. FindGigCommand searches all gig titles without changing the filtered client list.
  • deletes gigs by stable UID through Model#deleteGig and GigabyteData#removeGig. Any paid or unpaid obligation raises GigHasPaymentsException before mutation. Removing one observable-list entry preserves other references; the gig panel clears a removed selection before its filtered/sorted views process the removal.
  • deletes payments through Model#deletePaymentObligation, delegated to GigabyteData. Removal uses object identity to delete exactly one stored instance because separate obligations can have identical fields. DeletePaymentCommand resolves indexes using GigOrdering and PaymentObligationOrdering, as markpaid does. The observable removal refreshes the selected payment list or outstanding overview and its empty state. LogicManager saves the resulting data through the existing storage path after successful execution.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in GigabyteData, and each Client references tags from that list. This lets GigabyteData maintain one Tag object per unique tag instead of each Client holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save both Gigabyte data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonGigabyteDataStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)
  • serializes clients, gigs, and payment obligations through JsonAdaptedClient, JsonAdaptedGig, and JsonAdaptedPaymentObligation. Gigs store clientUid; payment obligations store gigUid; monetary values are stored as integer cents.
  • reads only the current save format through JsonUtil.readJsonFileStrict, rejecting unknown fields and fractional values for integer fields. The adapters require all three top-level arrays and each record's required fields; IDs and titles are never generated during loading. Older formats fail with DataLoadingException. User preferences continue to use the separate, permissive JsonUtil.readJsonFile path.
  • migrates data/addressbook.json to data/gigabyte.json during MainApp.init, before loading data, if the current file does not exist. JsonGigabyteDataStorage.migrateLegacyDataFile moves the file without changing its contents or replacing an existing destination. An IOException during migration stops startup.

The save-file fields are:

Object Required fields
Root clients, gigs, paymentObligations (arrays, including when empty)
Client uid, name, phone, email, address, tags
Gig uid, clientUid, title, status, deadline, feeCents
Payment obligation gigUid, amountCents, dueDate, paid

UUIDs must be valid, references must resolve to saved records, titles must be valid text, and monetary values must be positive integer cents. Null collections and null records are rejected. There is no automatic conversion of persons, name- or index-based references, decimal amount fields, or missing IDs and titles.

Data file format

MainApp uses data/gigabyte.json for application data and preferences.json for GUI preferences. Both paths are relative to the process's working directory. JsonSerializableGigabyteData stores three top-level arrays: clients, gigs, and paymentObligations. The following is a complete example with one record of each type:

{
  "clients": [
    {
      "uid": "11111111-1111-4111-8111-111111111111",
      "name": "Jamie Tan",
      "phone": "81234567",
      "email": "jamie@example.com",
      "address": "10 Clementi Road",
      "tags": []
    }
  ],
  "gigs": [
    {
      "uid": "22222222-2222-4222-8222-222222222222",
      "clientUid": "11111111-1111-4111-8111-111111111111",
      "title": "Website redesign",
      "status": "IN_PROGRESS",
      "deadline": "2027-06-30",
      "feeCents": 125050
    }
  ],
  "paymentObligations": [
    {
      "gigUid": "22222222-2222-4222-8222-222222222222",
      "amountCents": 50000,
      "dueDate": "2027-07-15",
      "paid": false
    }
  ]
}

feeCents and amountCents are positive integer counts of cents; the example represents a fee of 1250.50 and a payment of 500.00. Fee uses BigDecimal in memory and converts to and from BigInteger cents for storage. Dates use yyyy-MM-dd. The stored paid boolean records whether an obligation is settled; overdue status is derived from the due date and the current local date rather than stored separately.

Loading proceeds in dependency order: clients, then gigs, then payment obligations. The adapters resolve clientUid and gigUid to the canonical objects already loaded. Duplicate client records or client/gig UUIDs, unresolved parent references, and invalid field values detected during conversion cause the load to fail instead of returning partially loaded data.

Backward compatibility and filename migration

There is no schema-version field. The v1.4 loader accepts only the current required fields described above. It does not convert a v1.3 JSON shape: persons, absent collections or UUIDs, clientName, gigIndex, decimal fee/amount, and missing titles fail strict loading. JsonGigabyteDataStorage#migrateLegacyDataFile only moves data/addressbook.json to data/gigabyte.json when the destination is absent. It does not transform its contents. When both files exist, the current filename takes precedence and neither file is moved.

This distinction matters during upgrade: a moved v1.3 file remains unsupported. Preserve a backup before launch; if loading fails, the app starts with an empty model and the next successful command overwrites the moved file. The manual compatibility test below checks both the filename move with current-format data and the rejection of a representative v1.3 file.

Save lifecycle and failure behavior

LogicManager#execute performs these steps in order:

  1. Parse the input into a command.
  2. Execute the command against the model.
  3. Save the complete current GigabyteData through StorageManager and JsonGigabyteDataStorage.
  4. Return the CommandResult to the UI.

Every command that completes step 2 reaches the save step, including commands such as list that do not change stored records. A parsing or command-execution exception skips the save step. Missing parent directories and the data file are created when saving.

If saving throws AccessDeniedException, LogicManager reports insufficient write permissions through a CommandException. Other IOExceptions produce a CommandException containing the underlying error. The command's successful result is not returned to the UI, but any changes already made to the in-memory model remain: there is no rollback. After the write problem is resolved, the next successful command and save persist the current model, including those earlier unsaved changes.

FileUtil#writeToFile writes directly to the destination file. There is no temporary-file replacement or automatic backup, so a failed write does not guarantee that the previous file contents remain intact.

At startup, a missing data file causes MainApp to use sample data. A malformed JSON file or a validation failure reported as DataLoadingException is logged and causes the app to start with empty data. Loading itself does not overwrite that file, but the next successful save, even after list, replaces it with the current model. Preserve the original file before running commands when investigating a load failure.

GUI preferences are saved separately during initialization and shutdown. Missing or unreadable preferences fall back to defaults; failures to save preferences are logged. Shutdown does not provide an additional application-data save, so it does not retry a failed command save.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Stable client, gig, and payment links

Each Client and Gig has an immutable UUID. A Gig holds the canonical Client object from GigabyteData, while a PaymentObligation holds the canonical Gig object. The JSON format persists these relationships as clientUid and gigUid, avoiding ambiguous links when clients or gigs have equal display fields.

When a client is edited, GigabyteData#setClient rebuilds that client's immutable gigs with Gig#withClient and then relinks payment obligations to the replacement gig objects. Gig#withClient preserves the gig UUID and title, so editing contact details does not break payment links or discard gig information. During loading, storage resolves clientUid and gigUid against the saved UUIDs and rejects missing or invalid references.

EditPaymentCommand resolves the displayed client, per-client gig, and due-date-ordered payment indexes before it creates a replacement with PaymentObligation#withDetails. GigabyteData#setPaymentObligation searches for the selected stored object by identity before falling back to value equality, so editing one of two equal-valued payments changes only the indexed occurrence. The replacement keeps the stored gig object and paid state. Replacing the item in the observable payment list immediately updates and reorders the selected-gig and outstanding payment views.

MarkPaymentPaidCommand and MarkPaymentUnpaidCommand resolve the displayed client, per-client gig, and due-date-ordered payment indexes before changing any data. They reject a request that already matches the stored paid state, then call Model#setPaymentPaidState. GigabyteData replaces the selected object by identity with PaymentObligation#withPaid, which preserves its gig, amount, and due date and keeps equal-valued obligations independent. The observable-list replacement refreshes selected-gig and outstanding views immediately, while normal storage saving persists the corrected state.

EditGigCommand resolves both indexes before constructing a replacement gig with the same UID. Model#setGig relinks dependent payments to that replacement, so changing a title, deadline, or fee does not detach payments. DeleteGigCommand also resolves the normal per-client index first, but Model#deleteGig refuses removal while any paid or unpaid payment refers to the gig UID. The user must explicitly delete those payments, then retry the gig deletion. DeleteClientCommand similarly refuses to remove a client while gigs refer to its UID. clear is the explicit operation that removes the complete graph of clients, gigs, and payments at once. These policies preserve referential integrity and avoid silent dependent-record deletion.

FindGigCommand searches all titles with GigTitleContainsKeywordsPredicate; MainWindow displays the matching gigs without changing the filtered client list. Overview row positions are not command gig indexes. Commands use GigOrdering.forClient for a client's recorded gig order and PaymentObligationOrdering.forGig for due-date-ordered payments, including when another view is open.

Appendix: Requirements

Product scope

Target user profile:

  • is a freelancer who needs to manage multiple clients, gigs, deadlines, fees, and expected payments
  • prefers desktop apps over other types of applications
  • can type fast
  • prefers typing to mouse interactions
  • is reasonably comfortable using CLI apps

Value proposition: Track client work and expected payments quickly through a command-driven desktop application.

User stories

Priorities: High (must have) - * * *, Medium (nice to have) - * *, Low (unlikely to have) - *

Priority As a … I want to … So that I can…
* * * new freelancer user see instructions for available commands learn how to use Gigabyte
* * * freelancer add and edit a client keep contact details current
* * * freelancer delete a client without gigs remove unneeded contact records
* * * freelancer find a client by name locate a contact quickly
* * * freelancer record a payment obligation linked to a gig, with an amount and due date know what payment I expect and when

* * * freelancer view a client’s details and associated gigs understand my work with that client

* * * freelancer correct a gig's title, deadline, or fee keep work details accurate
* * * freelancer delete a gig after its payments are removed remove cancelled work without orphaning payments
* * * freelancer find gigs by title locate work across clients
* * * freelancer view upcoming gig deadlines in date order prioritise my work
* * freelancer filter gigs by status and review unpaid payments focus on active work and money owed

Use cases

For all use cases below, the System is the Gigabyte and the Actor is the freelancer, unless specified otherwise.

Use case: Create and progress a gig for a displayed client

Preconditions: The client already exists and is visible in the current client list.

MSS

  1. Freelancer identifies the client's displayed index.

  2. Freelancer enters addgig with a title, initial status, deadline, and agreed fee.

  3. Gigabyte validates the index and all four fields.

  4. Gigabyte creates the gig, links it to the client, saves the data, and confirms the new gig details.

  5. Freelancer identifies the new gig's position within that client's gig list.

  6. Freelancer enters setstatus with the displayed client index, gig index, and next status.

  7. Gigabyte validates the indexes and status.

  8. Gigabyte updates and saves the gig while preserving its client, title, deadline, fee, UID, and payments.

    Use case ends.

Extensions

  • 1a. The required client is not visible because the client list is filtered.
    • 1a1. Freelancer runs list or a suitable find command and resumes at step 1 using the newly displayed index.
  • 3a. The client index is invalid.
    • 3a1. Gigabyte reports that the client index is invalid without creating a gig.
  • 3b. The title, status, deadline, or fee is invalid.
    • 3b1. Gigabyte explains the relevant constraint without creating a gig.
  • 7a. Either index or the requested status is invalid.
    • 7a1. Gigabyte reports the error without changing the gig.
  • 7b. The gig already has the requested status.
    • 7b1. Gigabyte reports that no change was made.

Use case: Correct gig details

Preconditions: A client and one of their gigs exist.

MSS

  1. Freelancer identifies the displayed client index and that client's normal gig index.
  2. Freelancer enters editgig with one or more of a title, deadline, and fee.
  3. Gigabyte resolves the gig and validates all supplied fields before mutation.
  4. Gigabyte replaces the gig while retaining its UID, client, status, and linked payments, then saves the data.
  5. The selected gig view refreshes; a changed deadline reorders the deadline overview when it is open.

Extensions

  • 2a. No editable field or a repeated field is supplied.
    • 2a1. Gigabyte rejects the command without changing data.
  • 3a. An index or field is invalid, or the resulting details are unchanged.
    • 3a1. Gigabyte reports the error and leaves the gig and payments unchanged.

Use case: Delete a gig safely

Preconditions: The client and gig exist.

MSS

  1. Freelancer identifies the displayed client index and the gig's normal per-client index.
  2. Freelancer enters deletegig with both indexes.
  3. Gigabyte checks that the gig has no paid or unpaid obligations.
  4. Gigabyte removes exactly that gig by UID, saves the data, and refreshes open gig views.

Extensions

  • 3a. The gig has one or more obligations.
    • 3a1. Gigabyte rejects deletion and instructs the freelancer to remove the payments with deletepayment first.
    • 3a2. After removing the payments, the freelancer resolves the current indexes and retries at step 2.
  • 2a. Either index is invalid.
    • 2a1. Gigabyte reports the invalid index without changing records.

Use case: Find gigs by title

MSS

  1. Freelancer enters findgig with one or more title keywords.
  2. Gigabyte searches all gig titles using case-insensitive complete-word OR matching.
  3. Gigabyte displays matching gigs across all clients in recorded order, without changing the filtered client list.
  4. Freelancer selects a result to inspect its payments.

Extensions

  • 1a. No keyword is supplied.
    • 1a1. Gigabyte rejects the command.
  • 3a. No title matches.
    • 3a1. Gigabyte displays the no-matches message in the gig panel.

Use case: Record a payment obligation

Preconditions: The client and gig already exist.

MSS

  1. Freelancer identifies the client's displayed index and the gig's position within that client's gig list.

  2. Freelancer enters addpayment with both indexes, an amount, and a due date.

  3. Gigabyte validates the indexes, amount, and due date.

  4. Gigabyte records the obligation as unpaid, links it to the gig, saves the data, and confirms the amount and due date.

    Use case ends.

Extensions

  • 3a. Either index is invalid.
    • 3a1. Gigabyte reports whether the client index or per-client gig index is invalid without recording an obligation.
  • 3b. The amount or due date is invalid.
    • 3b1. Gigabyte explains the relevant constraint without recording an obligation.

Use case: Edit a payment obligation

Preconditions: The relevant client, gig, and payment obligation already exist.

MSS

  1. Freelancer identifies the displayed client index, the gig's position within that client's normal gig list, and the payment's position in the gig's due-date-ordered payment list.

  2. Freelancer enters editpayment with all three indexes and a replacement amount, due date, or both.

  3. Gigabyte resolves all three indexes before changing the obligation.

  4. Gigabyte validates the replacement fields and confirms that the resulting obligation is different.

  5. Gigabyte replaces and saves the selected obligation while preserving its gig and paid state.

  6. Gigabyte refreshes the visible payment view and reorders the row if its due date changed.

    Use case ends.

Extensions

  • 2a. Neither editable field is supplied, or a single-valued prefix is repeated.
    • 2a1. Gigabyte reports the input error without changing any obligation.
  • 3a. Any index is invalid.
    • 3a1. Gigabyte reports which displayed index is invalid without changing any obligation.
  • 4a. The amount or due date is invalid.
    • 4a1. Gigabyte explains the relevant constraint without changing any obligation.
  • 4b. The replacement details equal the selected obligation's existing details.
    • 4b1. Gigabyte reports that no change was made.

Use case: Record and settle a payment obligation

Preconditions: The relevant gig already exists in Gigabyte.

MSS

  1. Freelancer identifies the displayed client index and the gig's position within that client's gig list.

  2. Freelancer enters addpayment with both indexes, an amount, and a due date.

  3. Gigabyte validates and records the obligation as unpaid.

  4. Freelancer enters outstanding.

  5. Gigabyte shows unpaid obligations across all gigs in due-date order.

  6. Freelancer selects the client and gig to see that gig's numbered payment rows.

  7. Freelancer enters markpaid with the displayed client, gig, and payment indexes.

  8. Gigabyte validates the indexes, saves the paid state, refreshes the payment row, and confirms the change.

    Use case ends.

Extensions

  • 3a. The amount, due date, or either parent index is invalid.

    • 3a1. Gigabyte explains the error without creating an obligation. Use case resumes at step 2.

  • 8a. The selected obligation is already paid.

    • 8a1. Gigabyte informs the freelancer that no change was made. Use case ends.

Use case: Correct a payment marked as paid

Preconditions: The payment obligation exists and is marked as paid.

MSS

  1. Freelancer identifies the displayed client index, the gig's position within that client's gig list, and the payment's position in the gig's due-date-ordered payment list.
  2. Freelancer enters markunpaid with all three indexes.
  3. Gigabyte validates the indexes and confirms that the selected obligation is paid.
  4. Gigabyte saves the obligation as unpaid while preserving its gig, amount, and due date.
  5. Gigabyte refreshes the payment view and includes the obligation in outstanding as OVERDUE or OUTSTANDING according to its due date and the current local date.

Use case: Delete a payment obligation

Preconditions: The relevant payment obligation exists in Gigabyte.

MSS

  1. Freelancer identifies the displayed client index, per-client gig index, and per-gig payment index.

  2. Freelancer enters deletepayment with all three indexes.

  3. Gigabyte validates the indexes and deletes exactly that obligation, whether paid or unpaid, without a confirmation prompt. The gig, client, and other obligations are preserved.

  4. Gigabyte refreshes the payment view, saves the deletion, and reports the client, gig, amount, due date, and previous paid state. If the view is now empty, it shows the existing empty state.

    Use case ends.

Extensions

  • 3a. Any index is invalid.
    • 3a1. Gigabyte reports which displayed index is invalid without changing any obligation.

Use case: Review active deadlines

Preconditions: At least one gig exists.

MSS

  1. Freelancer enters deadlines.

  2. Gigabyte shows every non-completed gig across all clients, ordered by earliest deadline.

  3. Gigabyte labels deadlines before the current local date as OVERDUE and includes the client, title, status, deadline, and fee for each result.

  4. Freelancer selects a client to return to that client's normal gig list.

    Use case ends.

Extensions

  • 2a. There are no non-completed gigs.
    • 2a1. Gigabyte displays There are no active gig deadlines..

Non-Functional Requirements

  1. Platform and distribution: Gigabyte should run on mainstream desktop operating systems with Java 25 or above installed, and be distributed as a single JAR file that requires no installer.
  2. Offline use and persistence: Gigabyte’s core client, gig, and payment workflows should work without a remote server or network connection. Changes should be saved locally and remain available after the application is closed and reopened.
  3. Capacity and performance: Gigabyte should support up to 1,000 clients, 5,000 gigs, and 5,000 payment obligations without noticeable sluggishness during typical use. On a supported computer, searches, filters, and deadline or due-date views should display results within 2 seconds.
  4. Command-based usability: Users should be able to complete the main workflows by typing commands, without needing a mouse. For regular English text, users with above-average typing speed should be able to complete most tasks faster with commands than with the mouse.
  5. Display compatibility: Gigabyte should remain usable at 1280×720 with 150% screen scaling, and work well at 1920×1080 with 100% or 125% scaling.
  6. Data integrity and validation: Gigabyte should maintain valid links between gigs and clients, and between payment obligations and gigs. It should reject invalid dates and fees with clear error messages.

Glossary

  • Client: A person or organization that engages the freelancer for work.
  • Gig: A piece of work undertaken for a client, with its own deadline, agreed fee, and status.
  • Mainstream OS: Windows, Linux, Unix, or macOS
  • Outstanding payment: A payment obligation that has not been marked as paid.
  • Overdue payment: An outstanding payment whose due date is before the current date.
  • Private contact detail: A contact detail that is not meant to be shared with others
  • Payment obligation: An amount the freelancer expects to receive for a gig, with a due date and payment status.

Appendix: Instructions for manual testing

Given below are instructions to test the app manually.

Preparation: Build the release candidate with gradlew shadowJar (macOS/Linux: ./gradlew shadowJar) and copy build/libs/gigabyte.jar into an otherwise empty test folder. Unless a test says otherwise, launch it from that folder with java -jar gigabyte.jar. Back up data/gigabyte.json before any test that changes or corrupts it.

    1. Input: addgig 1 t/ s/NOT_STARTED d/2027-06-30 f/100

    2. Input: addgig 1 t/ followed by a 101-character title, then s/NOT_STARTED d/2027-06-30 f/100.

    3. Input: addgig 1 t/ Short title s/NOT_STARTED d/2027-06-30 f/100

  4. Repeated prefix

    1. Input: addgig 1 t/First t/Second s/NOT_STARTED d/2027-06-30 f/100

  5. Invalid client indexes

    1. Repeat a valid addgig command using client indexes 0, -1, abc, and 999.
