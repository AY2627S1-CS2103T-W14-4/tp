Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, ClientListPanel, GigListPanel, PaymentObligationListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts. Selecting a client in ClientListPanel passes that client to GigListPanel, which filters the observable gig list by the client's stable identifier and renders each gig's title, status, deadline, and fee. Selecting a gig then passes it to PaymentObligationListPanel, which shows that gig's due-date-ordered payments and their paid, outstanding, or overdue display states. MainWindow also switches these panels into the cross-client gigs, findgig, deadlines, and outstanding overview modes based on fields carried by CommandResult (see Cross-client gig and payment views).

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Client, Gig, and PaymentObligation objects from the model.
  • displays gigs and payments for the current selection without changing the client filter used by commands.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to a GigabyteParser object, which in turn creates a parser that matches the command (e.g., DeleteClientCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteClientCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a client).
    The command may make several calls to the Model; interactions within the model are omitted from this diagram.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

How the parsing works:

  • When called upon to parse a user command, the GigabyteParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddClientCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddClientCommand). The GigabyteParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddClientCommandParser and DeleteClientCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.
  • AddGigCommandParser parses one displayed client index plus t/, s/, d/, and f/ fields. AddPaymentCommandParser parses displayed client and per-client gig indexes plus a/ and d/ fields. Both reject missing or repeated single-valued prefixes before their commands update the model.
  • EditGigCommandParser accepts a displayed client index, a per-client gig index, and at least one of t/, d/, or f/. It rejects s/, so status changes always go through setstatus. DeleteGigCommandParser accepts the two indexes only. FindGigCommandParser accepts title keywords and rejects an empty query. SetGigStatusCommandParser parses two indexes and one s/ field. EditPaymentCommandParser parses three indexes and at least one of a/ or d/; DeletePaymentCommandParser, MarkPaymentPaidCommandParser, and MarkPaymentUnpaidCommandParser parse three indexes only. FilterGigsCommandParser parses one s/ field.
  • Some prefixes are shared by different commands (e.g., t/ is a tag for add but a title for addgig, and a/ is an address for add but an amount for addpayment). Each XYZCommandParser passes only the prefixes it accepts to ArgumentTokenizer, so the meaning of a prefix depends on the command being parsed.
  • ParserUtil reports the rejected value with title, status, deadline, and fee constraint errors. It caps the displayed value at 80 characters and replaces control characters before including it in the message.
  • summary, list, clear, help, and exit have no parser class: GigabyteParser creates these commands directly and ignores any arguments. deadlines and outstanding are also created directly, but GigabyteParser rejects any arguments supplied to them. Overview commands return CommandResult view instructions that MainWindow applies without changing the current client filter.

Model component

API : Model.java

The Model component,

  • stores all Client, Gig, and PaymentObligation objects. Clients are contained in a UniqueClientList; gigs and payment obligations are exposed as unmodifiable observable lists.
  • stores the Client objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Client> that the UI can observe and bind to, so the UI updates when the list changes.
  • uses stable UUIDs to preserve links from each gig to its client and from each payment obligation to its gig. Client edits replace linked immutable objects while retaining those identifiers and links. Payment edits replace the selected immutable obligation while preserving its canonical gig and paid state. Payment-status changes replace the exact immutable obligation while retaining its gig, amount, and due date.
  • replaces gigs through Model#setGig when details or status change. GigabyteData#setGig relinks dependent payments to the replacement object. EditGigCommand preserves the gig UID, client, status, and payments; a deadline edit refreshes and can reorder the deadline overview. FindGigCommand searches all gig titles without changing the filtered client list.
  • deletes gigs by stable UID through Model#deleteGig and GigabyteData#removeGig. Any paid or unpaid obligation raises GigHasPaymentsException before mutation. Removing one observable-list entry preserves other references; the gig panel clears a removed selection before its filtered/sorted views process the removal.
  • deletes payments through Model#deletePaymentObligation, delegated to GigabyteData. Removal uses object identity to delete exactly one stored instance because separate obligations can have identical fields. DeletePaymentCommand resolves indexes using GigOrdering and PaymentObligationOrdering, as markpaid does. The observable removal refreshes the selected payment list or outstanding overview and its empty state. LogicManager saves the resulting data through the existing storage path after successful execution.
  • defines the order in which a client's gigs and a gig's payment obligations are numbered, through the GigOrdering and PaymentObligationOrdering utility classes. Commands and the UI both use these classes, so a displayed index always refers to the same object in both places.
  • uses CommandUtil in indexed commands to resolve the displayed client, its gig, and that gig's payment obligation. The helper centralizes out-of-range checks and delegates gig and payment list ordering to the ordering utilities.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in GigabyteData, and each Client references tags from that list. This lets GigabyteData maintain one Tag object per unique tag instead of each Client holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save both Gigabyte data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonGigabyteDataStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)
  • serializes clients, gigs, and payment obligations through JsonAdaptedClient, JsonAdaptedGig, and JsonAdaptedPaymentObligation. Gigs store clientUid; payment obligations store gigUid; monetary values are stored as integer cents.
  • reads only the current save format through JsonUtil.readJsonFileStrict, rejecting unknown fields and fractional values for integer fields. JsonAdaptedGig and JsonAdaptedPaymentObligation read feeCents, amountCents and paid through StrictJsonDeserializers, which accept only a JSON integer or a JSON boolean and reject quoted values such as "5025" or "true" instead of converting them. The adapters require all three top-level arrays and each record's required fields; IDs and titles are never generated during loading. Older formats fail with DataLoadingException. User preferences continue to use the separate, permissive JsonUtil.readJsonFile path.
  • migrates data/addressbook.json to data/gigabyte.json during MainApp.init, before loading data, if the current file does not exist. JsonGigabyteDataStorage.migrateLegacyDataFile moves the file without changing its contents or replacing an existing destination. An IOException during migration stops startup.

The save-file fields are:

Object Required fields
Root clients, gigs, paymentObligations (arrays, including when empty)
Client uid, name, phone, email, address, tags
Gig uid, clientUid, title, status, deadline, feeCents
Payment obligation gigUid, amountCents, dueDate, paid

UUIDs must be valid, references must resolve to saved records, titles must be valid text, and monetary values must be positive JSON integers of cents. paid must be JSON true or false. Null collections and null records are rejected. There is no automatic conversion of quoted numbers or booleans, persons, name- or index-based references, decimal amount fields, or missing IDs and titles.

Data file format

MainApp uses data/gigabyte.json for application data and preferences.json for GUI preferences. Both paths are relative to the process's working directory. JsonSerializableGigabyteData stores three top-level arrays: clients, gigs, and paymentObligations. The following is a complete example with one record of each type:

{
  "clients": [
    {
      "uid": "11111111-1111-4111-8111-111111111111",
      "name": "Jamie Tan",
      "phone": "81234567",
      "email": "jamie@example.com",
      "address": "10 Clementi Road",
      "tags": []
    }
  ],
  "gigs": [
    {
      "uid": "22222222-2222-4222-8222-222222222222",
      "clientUid": "11111111-1111-4111-8111-111111111111",
      "title": "Website redesign",
      "status": "IN_PROGRESS",
      "deadline": "2027-06-30",
      "feeCents": 125050
    }
  ],
  "paymentObligations": [
    {
      "gigUid": "22222222-2222-4222-8222-222222222222",
      "amountCents": 50000,
      "dueDate": "2027-07-15",
      "paid": false
    }
  ]
}

feeCents and amountCents are positive integer counts of cents; the example represents a fee of 1250.50 and a payment of 500.00. Fee uses BigDecimal in memory and converts to and from BigInteger cents for storage. Dates use yyyy-MM-dd. The stored paid boolean records whether an obligation is settled; overdue status is derived from the due date and the current local date rather than stored separately.

Loading proceeds in dependency order: clients, then gigs, then payment obligations. The adapters resolve clientUid and gigUid to the canonical objects already loaded. Duplicate client records or client/gig UUIDs, unresolved parent references, and invalid field values detected during conversion cause the load to fail instead of returning partially loaded data.

Backward compatibility and filename migration

There is no schema-version field. The v1.4 loader accepts only the current required fields described above. It does not convert a v1.3 JSON shape: persons, absent collections or UUIDs, clientName, gigIndex, decimal fee/amount, and missing titles fail strict loading. JsonGigabyteDataStorage#migrateLegacyDataFile only moves data/addressbook.json to data/gigabyte.json when the destination is absent. It does not transform its contents. When both files exist, the current filename takes precedence and neither file is moved.

This distinction matters during upgrade: a moved v1.3 file remains unsupported. Preserve a backup before launch; if loading fails, the app starts with an empty model and the next successful command overwrites the moved file. The manual compatibility test below checks both the filename move with current-format data and the rejection of a representative v1.3 file.

Save lifecycle and failure behavior

LogicManager#execute performs these steps in order:

  1. Parse the input into a command.
  2. Execute the command against the model.
  3. Save the complete current GigabyteData through StorageManager and JsonGigabyteDataStorage.
  4. Return the CommandResult to the UI.

Every command that completes step 2 reaches the save step, including commands such as list that do not change stored records. A parsing or command-execution exception skips the save step. Missing parent directories and the data file are created when saving.

If saving throws AccessDeniedException, LogicManager reports insufficient write permissions through a CommandException. Other IOExceptions produce a CommandException containing the underlying error. The command's successful result is not returned to the UI, but any changes already made to the in-memory model remain: there is no rollback. After the write problem is resolved, the next successful command and save persist the current model, including those earlier unsaved changes.

FileUtil#writeToFile writes directly to the destination file without temporary-file replacement or a backup before each save, so a failed write does not guarantee that the previous file contents remain intact.

At startup, a missing data file causes MainApp to use sample data. A malformed JSON file or a validation failure reported as DataLoadingException causes MainApp to request a backup through Storage#backupGigabyteData before starting with empty data. JsonGigabyteDataStorage copies the original bytes to the first available sibling path <filename>_backup-N, starting at 1 (for example, gigabyte.json_backup-1). The copy never replaces an existing file or directory; a filename collision advances to the next number. The original file is not changed at startup. MainApp passes a warning and the backup path through UiManager to the main window's command result area. After a successful backup, the next successful save, even after list, replaces the original with the current model while preserving the backup.

If the backup fails, storage blocks data saves and the startup warning explains how to recover. LogicManager rejects commands before they change the model; only help and exit are allowed, and these skip saving in this state. Users must close the app, back up or repair the original file and resolve the backup failure, then restart. The storage write guard also prevents direct saves from overwriting the unprotected original. Backups are retained for manual recovery; they are not automatically repaired or restored.

GUI preferences are saved separately during initialization and shutdown. If preferences.json is missing, malformed, has "guiSettings": null, or contains a GUI-setting value of the wrong type, MainApp starts with default window settings and writes those defaults to preferences.json. Valid saved window size and position are restored. Failures to save preferences are logged. Shutdown does not provide an additional application-data save, so it does not retry a failed command save.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Stable client, gig, and payment links

Each Client and Gig has an immutable UUID. A Gig holds the canonical Client object from GigabyteData, while a PaymentObligation holds the canonical Gig object. The JSON format persists these relationships as clientUid and gigUid, avoiding ambiguous links when clients or gigs have equal display fields.

When a client is edited, GigabyteData#setClient rebuilds that client's immutable gigs with Gig#withClient and then relinks payment obligations to the replacement gig objects. Only affected rows are replaced in the observable lists, preserving unrelated stored objects and selections. Gig#withClient preserves the gig UUID and title, so editing contact details does not break payment links or discard gig information. During loading, storage resolves clientUid and gigUid against the saved UUIDs and rejects missing or invalid references.

EditPaymentCommand resolves the displayed client, per-client gig, and due-date-ordered payment indexes before it creates a replacement with PaymentObligation#withDetails. GigabyteData#setPaymentObligation searches for the selected stored object by identity before falling back to value equality, so editing one of two equal-valued payments changes only the indexed occurrence. The replacement keeps the stored gig object and paid state. Replacing the item in the observable payment list immediately updates and reorders the selected-gig and outstanding payment views.

MarkPaymentPaidCommand and MarkPaymentUnpaidCommand resolve the displayed client, per-client gig, and due-date-ordered payment indexes before changing any data. They reject a request that already matches the stored paid state, then call Model#setPaymentPaidState. GigabyteData replaces the selected object by identity with PaymentObligation#withPaid, which preserves its gig, amount, and due date and keeps equal-valued obligations independent. The observable-list replacement refreshes selected-gig and outstanding views immediately, while normal storage saving persists the corrected state.

EditGigCommand resolves both indexes before constructing a replacement gig with the same UID. Model#setGig relinks dependent payments to that replacement, so changing a title, deadline, or fee does not detach payments. DeleteGigCommand also resolves the normal per-client index first, but Model#deleteGig refuses removal while any paid or unpaid payment refers to the gig UID. The user must explicitly delete those payments, then retry the gig deletion. DeleteClientCommand similarly refuses to remove a client while gigs refer to its UID. clear is the explicit operation that removes the complete graph of clients, gigs, and payments at once. These policies preserve referential integrity and avoid silent dependent-record deletion.

FindGigCommand searches all titles with GigTitleContainsKeywordsPredicate; MainWindow displays the matching gigs without changing the filtered client list. Overview row positions are not command gig indexes. Commands use GigOrdering.forClient for a client's recorded gig order and PaymentObligationOrdering.forGig for due-date-ordered payments, including when another view is open.

Design considerations:

Aspect: How gigs and payment obligations refer to their owners:

  • Alternative 1 (current choice): Store a stable UUID for each client and gig, and save references as clientUid and gigUid.

    • Pros: Links stay correct when two clients or gigs have identical display fields, and when a client's name or a gig's title is edited.
    • Cons: The save file is harder to edit by hand, and older save files without IDs cannot be loaded.

  • Alternative 2: Refer to the owner by its name (for clients) or its position in a list (for gigs).

    • Pros: Simpler save format that is easier to read.
    • Cons: Renaming a client, reordering gigs, or having duplicate titles can silently move payments to the wrong gig.

Per-client gig and payment indexes

Gig and payment commands identify their target with nested indexes instead of one global index. For example, markpaid 2 1 3 means "the 3rd payment of the 1st gig of the 2nd displayed client". Commands resolve these indexes in the following order:

  1. The client index is resolved against Model#getFilteredClientList(), so it follows the client list currently on screen (including find results), just like AB3's delete and edit commands.
  2. The gig index is resolved against GigOrdering#forClient(model.getGigList(), client), which keeps the client's gigs in the order they appear in the stored gig list. (setstatus uses an equivalent filter on the stored gig list.)
  3. The payment index (for editpayment, markpaid, markunpaid, and deletepayment) is resolved against PaymentObligationOrdering#forGig(model.getPaymentObligationList(), gig), which sorts the gig's payments by due date and then by their position in the stored list.

All commands that take a gig index (addpayment, editgig, setstatus, deletegig, editpayment, markpaid, markunpaid, and deletepayment) resolve it this way. If any index is out of range, the command throws a CommandException before changing the model, so a command never changes some records and then fails.

GigListPanel and PaymentObligationListPanel use the same GigOrdering and PaymentObligationOrdering logic when displaying a selected client's gigs and a selected gig's payments. This keeps the numbers shown in those panels equal to the numbers that commands expect. The cross-client views (gigs, findgig, deadlines, and outstanding) are filtered or sorted differently, so their row numbers are only for display. Commands still use the per-client indexes, even while one of these views is visible.

Design considerations:

Aspect: How to identify a gig or payment obligation in a command:

  • Alternative 1 (current choice): Use nested indexes (client, then gig, then payment).

    • Pros: Indexes are short and stay stable while the user works within one client. They also match the client → gigs → payments layout of the GUI.
    • Cons: Commands need two or three indexes, and the row numbers in cross-client views cannot be used directly.

  • Alternative 2: Use one global index for each gig and payment obligation.

    • Pros: Commands are shorter, and every view could be used to pick a target.
    • Cons: Global indexes change whenever a gig or payment for any client is added or reordered, making them easy to mistype for users who manage many clients.

Editing a gig

editgig CLIENT_INDEX GIG_INDEX [t/TITLE] [d/DEADLINE] [f/FEE] corrects a gig's details without changing its identity, client, status, or payment obligations.

  1. EditGigCommandParser checks that exactly two indexes and at least one of t/, d/, and f/ are given, rejects s/ and repeated prefixes, and parses each supplied field into a GigTitle, Deadline, or Fee. Missing fields are passed to EditGigCommand as empty Optionals.
  2. EditGigCommand#execute resolves both indexes as described in Per-client gig and payment indexes.
  3. It creates the replacement with Gig#withDetails, which copies the target's UUID, client, and status and uses the target's existing value for every field that was not supplied. If the replacement equals the target, the command fails with The gig already has the specified details.
  4. It calls Model#setGig(target, replacement). GigabyteData#setGig finds the stored gig by UUID, checks that the replacement keeps the same UUID and client, replaces the gig in the observable gig list, and relinks the gig's payment obligations to the replacement object.

Payment amounts are stored separately from the gig's agreed fee, so changing the fee does not change any recorded payment. The gig views observe the gig list, so the selected client's gigs, status results, title search results, and the deadline overview update immediately. setstatus uses the same Model#setGig path, with Gig#withStatus creating the replacement.

GigListPanel captures the selected gig before its source list changes and restores its selection by UUID after filtering and sorting finish. Intermediate row changes do not switch the payment view. A deleted gig or one that leaves the active filter clears its selection and payments. ClientListPanel treats replacement details with the same client UUID as the same selection, preserving the current gig view during contact edits.

Design considerations:

Aspect: Whether editgig should also change the gig's status:

  • Alternative 1 (current choice): Reject s/ in editgig and keep setstatus as the only way to change status.

    • Pros: Each command has one clear purpose, and setstatus can report a status-specific error when the status is already set.
    • Cons: Users need two commands to change a gig's details and its status.

  • Alternative 2: Allow editgig to change every gig field, including status.

    • Pros: One command can update everything at once.
    • Cons: Two commands would then change status, with different validation and error messages.

Deleting linked records safely

Clients, gigs, and payment obligations form a chain of links: each gig refers to its client, and each payment obligation refers to its gig. Gigabyte never deletes a record that another record still refers to:

  • delete fails with Client cannot be deleted while it has associated gigs while any gig refers to the client's UID.
  • deletegig fails while any paid or unpaid payment obligation refers to the gig's UID. GigabyteData#removeGig checks this before changing anything and throws a GigHasPaymentsException, which DeleteGigCommand reports as a CommandException telling the user to delete the payments first with deletepayment.
  • deletepayment has no dependent records, so it succeeds for any valid index. GigabyteData removes the exact stored object, so deleting one of two identical payments removes only the indexed one.
  • clear is the only command that removes linked records together. It replaces all data with an empty GigabyteData.

Design considerations:

Aspect: What happens to linked records when a record is deleted:

  • Alternative 1 (current choice): Block the deletion until the user has deleted the linked records.

    • Pros: Records, including payments that are still owed, are never deleted by accident. This matters because there is no undo.
    • Cons: Deleting a gig that has several payments takes several commands.

  • Alternative 2: Cascade the deletion, removing a gig's payments (or a client's gigs and payments) with it.

    • Pros: One command removes everything that belongs to the record.
    • Cons: Payment records could be lost without the user noticing, and the data cannot be recovered.

Cross-client gig and payment views

By default, the Gigs panel shows the selected client's gigs, and the Payment obligations panel shows the selected gig's payments. Four commands switch these panels into views that cover all clients, without changing the client filter used by other commands:

Command CommandResult field set Panel method called by MainWindow
gigs s/STATUS gigStatusFilter GigListPanel#showGigsWithStatus
findgig KEYWORD... gigTitleSearch GigListPanel#showGigsMatchingTitle
deadlines showDeadlineOverview GigListPanel#showDeadlineOverview
outstanding showOutstandingPayments PaymentObligationListPanel#showOutstandingPayments

These commands do not change the Model. At most, they count the matching records for the feedback message. Each returns a CommandResult that describes the view to show. After Logic#execute returns, MainWindow#executeCommand checks these fields, clears the client (and, where needed, gig) selection, and calls the matching panel method.

Each panel wraps the model's observable list in a FilteredList and a SortedList. A view only replaces the predicate and comparator. For example, deadlines keeps non-completed gigs and sorts them by deadline, while findgig uses a GigTitleContainsKeywordsPredicate and keeps the stored order. Because the panels still observe the model's lists, later edits, status changes, payment updates, and deletions appear in the current view immediately. Selecting a client calls GigListPanel#showGigsFor, which leaves the cross-client view and shows that client's gigs again.

Design considerations:

Aspect: Where the state of the current view is kept:

  • Alternative 1 (current choice): The command returns view instructions in CommandResult, and the UI keeps the view state.

    • Pros: Model stays free of display-only state, and switching views does not change the client filter that commands use for indexes.
    • Cons: CommandResult gains a field for each kind of view, and the view state cannot be unit tested through Model alone.

  • Alternative 2: Store the current gig and payment filters in Model, like AB3's filtered client list.

    • Pros: Consistent with how find and list work.
    • Cons: Commands would have to know which view is visible to interpret indexes, which makes nested indexes ambiguous.

Work and payment summary

summary shows a read-only overview of all stored data. SummaryCommand#execute:

  1. counts all clients through Model#getGigabyteData(), so the client filter set by find does not affect the count,
  2. counts gigs for each GigStatus, starting every status at zero so that statuses with no gigs are still shown, and
  3. adds up payment amounts in cents as BigInteger values. Unpaid payments are counted as Outstanding, unpaid payments with a due date before today are counted as Of which overdue, and paid payments are counted as Marked paid.

The command reads "today" from a java.time.Clock that defaults to the system clock. Tests pass a fixed clock so that results which depend on overdue dates stay deterministic.

[Proposed] Undo/redo feature

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedGigabyteData. It extends GigabyteData with an undo/redo history, stored internally as an gigabyteDataStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedGigabyteData#commit() -- Saves the current Gigabyte data state in its history.
  • VersionedGigabyteData#undo() -- Restores the previous Gigabyte data state from its history.
  • VersionedGigabyteData#redo() -- Restores a previously undone Gigabyte data state from its history.

These operations are exposed in the Model interface as Model#commitGigabyteData(), Model#undoGigabyteData() and Model#redoGigabyteData() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedGigabyteData will be initialized with the initial Gigabyte data state, and the currentStatePointer pointing to that single Gigabyte data state.

Step 2. The user executes delete 5 command to delete the 5th client in the Gigabyte data. The delete command calls Model#commitGigabyteData(), causing the modified state of the Gigabyte data after the delete 5 command executes to be saved in the gigabyteDataStateList, and the currentStatePointer is shifted to the newly inserted Gigabyte data state.

Step 3. The user executes add n/David …​ to add a new client. The add command also calls Model#commitGigabyteData(), causing another modified Gigabyte data state to be saved into the gigabyteDataStateList.

Note: If a command fails its execution, it will not call Model#commitGigabyteData(), so the Gigabyte data state will not be saved into the gigabyteDataStateList.

Step 4. The user now decides that adding the client was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoGigabyteData(), which will shift the currentStatePointer once to the left, pointing it to the previous Gigabyte data state, and restores the Gigabyte data to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial GigabyteData state, then there are no previous GigabyteData states to restore. The undo command uses Model#canUndoGigabyteData() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

[Proposed] Data archiving

Proposed Implementation

The proposed archiving mechanism would let freelancers move completed work out of their active data, while keeping it in a separate file for reference. It would be facilitated by an ArchiveCommand, a new Storage method, Storage#saveArchive(ReadOnlyGigabyteData archive, Path archiveFilePath), and a new Model method, Model#removeArchivedGigs(ReadOnlyGigabyteData archive).

Commands only receive the Model, so ArchiveCommand cannot save files itself. Instead, LogicManager, which already holds both the Model and the Storage, would coordinate the two saves, in the same way that it saves the active data after every command today.

Given below is an example usage scenario and how the archiving mechanism would behave.

Step 1. The user executes archive. ArchiveCommand#execute collects every gig whose status is COMPLETED and all of whose payment obligations are marked paid. Completed gigs that still have unpaid obligations are left in the active data, so money that is still owed stays visible in outstanding.

Step 2. ArchiveCommand builds a new GigabyteData containing the selected gigs, their payment obligations, and the clients they belong to. Because gigs and payments are linked by UUID, the archive can be saved in the existing save format. The command does not change the Model. It returns the archive to LogicManager in its CommandResult.

Step 3. LogicManager saves the archive to a new file whose name includes the date and time of the command, down to the second, e.g., data/archive/gigabyte-2027-01-31T14-05-09.json. Hyphens are used instead of colons so that the name is valid on Windows. Storage#saveArchive only creates new files: it opens the file with StandardOpenOption.CREATE_NEW, so it never replaces an existing archive, even when archive is run several times on the same day. If a file with that name already exists, or the save fails for any other reason, LogicManager throws a CommandException. The Model and the active data file have not been changed, so nothing needs to be rolled back, and the user can simply run archive again.

Step 4. Only after the archive is saved, LogicManager calls Model#removeArchivedGigs, which removes the archived gigs (matched by UUID) and their payment obligations from the active data. Clients are kept, even when all their gigs were archived, so that new gigs can still be added for them.

Step 5. LogicManager saves the active data as it does after every command. If this save fails, the error is reported as for any other failed save. The active data file on disk then still contains the archived records, so they exist in both files until the next successful save, but no record is lost.

Design considerations:

Aspect: Which component coordinates the two saves:

  • Alternative 1 (proposed choice): LogicManager saves the archive returned by the command, then updates the Model.

    • Pros: Commands keep depending only on Model. Saving the archive before changing the Model means a failed archive save never needs a rollback.
    • Cons: LogicManager gains logic that is specific to one command, and the two files are not updated atomically.

  • Alternative 2: Give ArchiveCommand access to Storage so that it saves the archive itself.

    • Pros: All archiving logic is kept in one class.
    • Cons: Breaks the current architecture, in which commands interact only with the Model, and makes the command harder to test with a model stub.

Aspect: Where archived records are kept:

  • Alternative 1 (proposed choice): Save archived records in a separate JSON file.

    • Pros: The active data file stays small, and the existing loading and validation code can read an archive file.
    • Cons: Archived records cannot be searched from within the app without a separate "view archive" feature.

  • Alternative 2: Keep archived records in the active data file with an archived flag.

    • Pros: Archived records can be restored, searched, and included in summary easily.
    • Cons: Every view and command would have to filter out archived records, and the save format would change.

Non-Functional Requirements

  1. Should work on any mainstream OS as long as it has Java 25 or above installed.
  2. Should be distributed as a single JAR file that does not need an installer.
  3. Should work without a network connection, saving all data locally so that it is still available after the app is closed and reopened.
  4. Should store data locally in a human-editable text file, without using a database management system (DBMS).
  5. Should be able to hold up to 1000 clients, 1000 gigs, and 1000 payment obligations without noticeable sluggishness in performance for typical usage.
  6. Should show the results of searches, filters, and overview commands within 2 seconds on a typical modern computer.
  7. A user with above average typing speed for regular English text (i.e. not code, not system admin commands) should be able to accomplish most of the tasks faster using commands than using the mouse.
  8. Should work well for screen resolutions of 1920×1080 and higher at screen scales of 100% and 125%, and remain usable for resolutions of 1280×720 and higher at a screen scale of 150%.
  9. Should never store a gig that refers to a missing client, or a payment obligation that refers to a missing gig.
  10. Should store and total monetary amounts exactly to the cent, without rounding errors.

Glossary

  • Active gig: A gig whose status is not COMPLETED.
  • Agreed fee: The amount a client has agreed to pay for a gig. It is stored separately from the gig's payment obligations.
  • Client: A person or organization that engages the freelancer for work.
  • Client index: The position of a client in the client list currently on screen, which may be filtered by find.
  • Gig: A piece of work undertaken for a client, with its own title, status, deadline, and agreed fee.
  • Gig index: The position of a gig in its client's gig list, counted from 1.
  • Mainstream OS: Windows, Linux, or macOS
  • Outstanding payment: A payment obligation that has not been marked as paid.
  • Overdue: Describes an active gig whose deadline, or an outstanding payment whose due date, is before the current date.
  • Payment index: The position of a payment obligation in its gig's payment list, which is ordered by due date.
  • Payment obligation: An amount the freelancer expects to receive for a gig, with a due date and payment status.
  • Private contact detail: A contact detail that is not meant to be shared with others
  • UID: A unique identifier that Gigabyte gives each client and gig, used to link records in the data file.

Appendix: Effort

Difficulty level

AB3 manages a single entity type (Person) in one list. Gigabyte manages three linked entity types: Client, Gig, and PaymentObligation. Each gig belongs to a client and each payment obligation belongs to a gig, so most features had to consider how a change to one record affects the records linked to it.

Challenges faced

  • Keeping links correct with immutable objects. Core domain entities such as Client, Gig, and PaymentObligation are immutable, following AB3's entity design. Editing a client or a gig therefore creates a new object, and every linked gig or payment obligation must be relinked to the replacement. Stable UUIDs, and the relinking logic in GigabyteData, were added so that records with identical display fields are never confused (see Stable client, gig, and payment links).
  • Nested indexes. Gig and payment commands take two or three indexes. The order used by commands and the order shown in the GUI had to be kept identical, while the cross-client views use a different order (see Per-client gig and payment indexes).
  • Several views of the same data. The gigs, findgig, deadlines, and outstanding views had to update immediately after edits, without changing the client filter that commands depend on (see Cross-client gig and payment views).
  • Safe deletion of linked records. Deleting a client or gig is blocked while other records still refer to it, and deleting one of two identical payments must remove only the indexed one (see Deleting linked records safely).
  • Strict and safe storage. The save format stores links by UUID and money as integer cents. Loading rejects unknown fields, missing fields, and broken references, and the old addressbook.json file name is migrated safely.
  • Exact money handling. Fees and payment amounts use BigDecimal and integer cents, so totals in summary are exact to the cent.

Reuse

The architecture, the Main and Commons code, the JSON storage framework, the GUI framework, and the test setup were reused from AB3. AB3's Person was adapted into Client. The Gig and PaymentObligation entities, their commands, parsers, storage adapters, and GUI panels, and the cross-client views were written by the team.

Achievements

Gigabyte extends AB3 with gig tracking (addgig, editgig, setstatus, deletegig, gigs, findgig, and deadlines), payment tracking (addpayment, editpayment, markpaid, markunpaid, deletepayment, and outstanding), and a work and payment summary. The GUI was extended from one list to three linked panels for clients, gigs, and payment obligations.
